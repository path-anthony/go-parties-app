# GO! Event Group · project log

## 2026-09-23

**Later the same day:** the skill model was wrong in two ways and both are fixed. An item's skill was one value and having one hid the item from units, treating "needs people" and "is a physical thing" as exclusive. Now `Item.skills` is a list (the 22 single values were carried over as one-element lists, nothing lost), any number can be checked in the item popup, and units are independent: a cigar bar can be two real setups that each need waitstaff, a bartender and a photographer. Booking such an item locks a unit and creates one gig per skill, each offered and filled on its own; cancelling cancels all of them; removing the unit from the booking takes its gigs with it. Availability is the tighter of the two: at least one free unit and, for every skill, at least one free person. The lock order is fixed (units first, then skills alphabetically across the whole booking) so two items sharing skills tagged in opposite order can't deadlock; a four-way concurrent booking across such items produced only 201s and 409s. On the way: the item popup gained a Units section (the count is the number of unit rows; add and remove there, removal refused while a live booking holds the unit), the Inventory table shows Units and Crew as separate columns, and "Price unit" is labelled "Billed per" so it can't be read as a count. And 144 items with no units and no skills each got a default "Unit #1", so the physical catalog is bookable once per date; the 22 skill-only items were left unit-less on purpose, since a unit on them would cap them at one booking a day regardless of crew.

**Where we are:** Crew and Gigs has its first real version, and it changes what a service item is. Seventeen catalog items (the four MC and DJ tiers, four Photography tiers, four Videography tiers, Photo Booth Packages 1 to 4, and Day of Planner) now carry a required skill, which makes them service items: a person's time, never a physical piece. They no longer need units and the API refuses units on them. Their availability is the crew: a service item is free on a date when the active crew members with its skill outnumber the gigs already needing that skill that day, checked under a lock inside the booking transaction so two customers racing for the last DJ take turns and exactly one wins (run on the live database). Booking one creates a Gig per unit of the item (Needs Crew); cancelling the booking cancels its gigs; rescheduling moves them and refuses the whole move if the crew can't cover the new date; the admin's booking popup can add or remove a service item the same way it adds or removes a unit. CrewMember (name, phone, email, skills from a fixed list, active, notes) and GigOffer (Sent, Accepted, Declined) round it out. The admin's Crew & Gigs nav entry, a stub since the first pass, is a real screen: a Gigs tab (every gig, filterable by status, each opening a popup that lists everyone active with the skill as a pre-checked list, records offers to the checked ones, and marks any offer accepted or declined, with a second accept on a filled gig refused by name) and a Crew tab (add, edit, deactivate). Overview's "Bookings needing crew" placeholder is live with a count and the soonest gigs. Nothing is sent to anyone yet; offers are the admin's record.

Twelve service-shaped items were left untagged on purpose because the name didn't settle it (additional hours and additional people, the edits, the two TBD booths, the enclosed booth with no attendant, the scrapbook add-on). They are one field each in the item popup once decided.

The same day, earlier: the admin login got the customer login's rate limit (5 failures per 15 minutes per IP), and deleting a catalog item became a real feature with a confirmation that names every package it will leave and auto-unpublishes any published package it would empty, refusing while a live booking holds the item.

**What we decided:** A service item is booked against people, not units, and no item is ever both. A gig is one person for one item on one booking, created and cancelled with the booking, never by hand. Skills are a fixed list in code, like every other fixed set here. Crew are deactivated, never deleted. The storefront needed no change: a service item reads as bookable with a free count, exactly like a physical one, and the portal lists it under the booking's items with the label Crew.

**What's next:** Real crew from Andy, which is what makes the seventeen service items bookable. Decide the twelve untagged items. Then SMS offers through n8n with accept-by-reply, and a rate per gig.

## 2026-09-22

**Where we are:** Since the 2026-09-17 entry, four arcs landed and one didn't move. Item photos show as thumbnails on Browse rows, the Ask GO list, cart rows and the held screen, with the photo plate where an item has none. Two storefront bugs were fixed on the way: a signed-in booking that lost its name when the cookie didn't travel, and a duplicate-booking race on the account step.

The eight pages and routes are deleted, the old paths redirect to Browse, Home's Continue button is now "See what's open" into Browse, the Book tab goes to Browse (and is the active tab on Browse and every `/item` screen) instead of asking for an occasion first, the booking store lost the fourteen fields and five methods only that flow used, and the scripted "About this package" Ask GO context that only its package screen opened went with it. And the white-glove concierge door, on the storefront side. Two entry points, one destination: a screen in checkout right after the date (`/item/:id/concierge`, the one step shared by guests and signed-in customers) and a nudge under an Ask GO recommendation when the admin's answer says `suggestConcierge`. Public responses are constructed field by field, never spread from a database row. The docs describe what the repos contain today; GO-PRODUCT and GO-ROADMAP were rewritten from the code and the live database, and the outstanding requirements (retainer collection, cancellation fee policy, contract e-sign, Crew and Gigs, video links on inventory, concierge routing, real wedding packages as test cases) are the roadmap's Next, in the order they unblock each other.

## 2026-09-17

**Where we are:** A signed-in direct booking could fail with the admin's "customerName is required" and lose the booking. The storefront knew the customer (the sign-in response sets it client-side) but left name, phone and email out of the booking request and trusted the session cookie to carry them; wherever the cookie doesn't travel (a different site in production, a browser that blocks it), the admin saw a request with nothing required in it. The request now always carries name, phone and email from the account the storefront knows, with the cookie still along so the booking attaches to the account. The failure display is fixed with it: the admin's raw wording is never shown except for a date that is taken or an item that isn't bookable; everything else is the bank's calm line with a Try again, and nothing typed is lost (every who-screen field lives in the booking store; the account step keeps its own). A sign-up that succeeded with a booking that failed after it hands the notice to the who screen.

Later the same day, a duplicate-booking race on the account step: a guest who made an account and tapped Hold my date once got a real booking and then a fresh form instead of the confirmation, and a second tap made a second real booking. The sign-up sets the customer, the booking succeeds, navigate() to held is deferred, and the hold's cleanup dropped `booking` back to false synchronously, so the render-time guard ("signed in, nothing in flight: go to the who screen") re-fired and its Navigate beat the pending one. `booking` now stays true on every path that leaves the screen (success, and the signed-up-then-failed hand-off, which had the same race and would have dropped its notice) and is reset only when the screen stays to show a notice. The guard stays render-time on purpose: a signed-in customer landing on that URL must be redirected before a guest form ever paints, and an effect would paint it first and still need the same in-flight check.

**What we decided:** Nothing required in a booking request may depend on a cookie arriving. Server validation text is for the console, not the screen. A screen that is leaving never re-arms its own guards.

**What's next:** Everything from 2026-09-16 still stands. The production cookie question (SameSite=None needs NODE_ENV=production on the admin, and Safari blocks third-party cookies regardless) still decides whether signed-in bookings attach to the account in production; the booking itself now succeeds either way.

## 2026-09-16

**Where we are:** Welcome and Home are one screen at `/` and `/home`: the photo carousel on top with the value props as per-slide captions, then the greeting and the three doors. The old click-through sign-in gate is gone; `/signin` redirects to the portal's sign in, which is reachable from the header Menu and My party at any time. The greeting is real: the customer's first name when signed in, "Hey there" otherwise. Production deep links were a real 404. The storefront deploys to Vercel (the 2026-09-10 note saying Railway was wrong, and the 2026-09-15 entry repeated it), and Vercel serves `dist/` as static files with no history fallback unless `vercel.json` says so. The rewrite that fixed this was deleted on 2026-09-10 on that wrong belief. `vercel.json` is back: every unmatched path rewrites to `index.html`. It takes effect on the next Vercel deploy (`npx vercel --prod`), which has to be run from the founder's terminal; it cannot be verified from inside the sandbox. `npm start` (Vite preview over `dist/`, single page fallback built in) stays as the local way to check a production build.

Later the same day: the static sub-occasion recommendations on Home are gone. Picking a sub-occasion asks the admin for its published packages (`GET /api/packages/public?occasion=`) and shows only those; a package is a pre-filled cart of its real items and books through the same direct checkout. No packages says so plainly.

And the pricing gap that opened is closed the same day: Booking carries `package_id` and `total`; `POST /api/bookings/direct` takes an optional `packageId`, checks it is a published package whose items are exactly the ones being booked, holds the package's quantity of units for each item (each lock skipping the units already held in the transaction), and records the bundle price as the total. Without a package the total is the item prices times quantity. The storefront shows the package price as the cart total, sends `packageId`, drops it the moment the cart is edited, and asks the calendar for enough units, not just one.

**What we decided:** A package books as itself or not at all: the admin refuses a package id whose items don't match the cart, and the storefront clears the package when anything is added or removed. The total the customer sees is the admin's number, not a sum the storefront made up. No gate in front of the product; sign in is a door, never a step. Value props that the screen already makes (a real package in seconds, the Ask GO card) are cut rather than repeated; the ones about dates and delivery ride the captions. The deploy fix lives in the repo (`vercel.json`), not in a dashboard setting, so it survives a rebuild.

**What's next:** Deploy to Vercel (`npx vercel --prod`) and open `/home` directly on the live site to confirm the 404 is gone; confirm `VITE_ADMIN_API_URL` is set in the Vercel project's build env. Everything from 2026-09-15 still stands.
