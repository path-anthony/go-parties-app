## Direct item booking (added 2026-09-15)

A second door, for a customer who wants specific things and not a package. Since Block S3 the order is: options (when the cart needs them), date, sign in or create an account (skipped when signed in), event details, the contract (tier 2), the retainer (tiers 1 and 2); an account is always required and there is no guest path. It is not a fifth tab (BRAND.md section 8). It is entered from an Ask GO recommendation: each recommended item has a checkbox, and one shared button ("Just this" for one, "Just these (2)" for more) carries every checked item into the same screens below on one date. The request goes as `itemId` for one item and `itemIds` for several, so an admin without multi-item support refuses the whole request rather than booking the first one. That response already carries real admin item ids, names, and prices, so it is the place the storefront picks real items. Calls go to go-parties-admin at the same base URL Ask GO uses.

The lookup is Places API (New) through the Maps JavaScript API's places library (`AutocompleteSuggestion.fetchAutocompleteSuggestions` with a session token, `includedRegionCodes: ["us"]`, a `locationBias` circle around Farmington; then `Place.fetchFields` for `id, formattedAddress, location, addressComponents`); a pick verifies only with a `street_number` and a `route`. The map is Google's with an advanced marker (`gmpDraggable`, `gmp-dragend`), map ID from `VITE_GOOGLE_MAPS_MAP_ID` or `DEMO_MAP_ID`. The verified address, the pin and the notes live in the store and are cleared only when the address text changes or the "later" switch is turned on. Customer bookings may carry `delivery: { formattedAddress, setupLat, setupLng, setupNotes, verified } | null`; the crew gig page's accepted state may carry `mapsUrl` (https only) for its "Open in Maps" button. `src/lib/maps.ts`, `src/lib/places.ts`, `src/components/go/AddressField.tsx`, `SetupMap.tsx`, `MiniMap.tsx`. Mock mode: any checkout mock (`?mock=tier1` and the others) and `?mock=portal` answer the lookup from `placesMock.ts` (14 Maple Lane and 228 Ridge Road verify; Farmington and Winding Trails do not) and draw the map as a plate the pin can be dragged across (`SetupMapMock.tsx`); all of it is behind `import.meta.env.DEV` and out of production builds.

Tiers (Block T2): `POST /api/bookings/tier` (body: the hold body minus contact, agreement and bot fields) answers `{ tier, reasons, total, retainerPercent, retainerAmount, policy, contract, quoteExpiresAt }`. Tier 1 ticks the rental policy (the `policy` from the tier answer, the settings copy as fallback) and holds; tier 2 reads and signs the GO contract in checkout; tier 3 holds nothing and answers 202 as before. The step counter: date, who, account (guest), contract (tier 2), retainer (tiers 1 and 2). Checkout mocks, dev only, chosen with `?mock=<name>` (`?mock=off` clears; nothing of this is in a production build): `tier1`, `tier1-nopay`, `tier2`, `tier2-expired`, `tier2-changed`, `tier2-retier, tier1-taken (S2: the first hold is refused `unavailable` with the admin's own words, the next one holds), tier1-account (S3: the first hold is refused 401 `account-required`, the next one holds). Under any checkout mock or `?mock=portal` the account calls are answered in memory (`src/lib/authMock.ts`): sign up with what was typed (an email containing "taken" answers the admin's 409), sign in as a returning customer with a home address, or without one when the email contains "nohome"; `PATCH /api/customer/me` with phone 860 555 0000 answers the 409`, `tier3`; they also stand in for the catalog and availability so Browse works with no admin. `?mock=portal` signs a fake customer in with a booking in every stage (Held with the retainer due, Requested with an unsigned contract, Signed with the retainer due, Confirmed with the balance due, In review, Proposal ready, Completed, Cancelled, Released); signing and paying change the fixtures in memory, and the payment form is a stand-in with a Simulate payment button that takes the same path as Stripe's completion.

Errors (Block S2): one style everywhere, `src/components/go/ErrorNotice.tsx`. `ErrorNotice` is red text on a light red ground with a red left rule and `role="alert"`, placed directly above the button whose action failed (between the body and the `Foot` on checkout, sign in, sign up, the portal contract and reschedule; above Send on Ask GO; above the Keep it / Cancel it pair on My party; above Submit bid / Decline, "I'm set" and "Send question" on the crew page; above Sign contract on `/sign/:token`) and scrolled into view when it appears. `FieldError` is the same red directly under a field that is in error, with `aria-invalid` on the Input for the red border (the unverified address, a taken phone or email on sign up). Catalog and package loads that fail (Home, the store, the availability check) use the same notice. Nothing that is an error is shown in white, grey or the normal text style; success and information keep their quiet styles. The kit (`/kit`) shows both.
